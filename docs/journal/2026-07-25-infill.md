# 2026-07-25 — the model that never learned to fill a blank

Wired the real checkpoint into the UI, ran the flagship infill demo — `18+__=45`, the trick left-to-right models structurally can't do — and the model filled the hole with padding tokens. Not wrong digits. Padding.

Two causes, both mine:

1. **Off-distribution canvas.** I served the infill as an 8-token canvas, exactly prefix+hole+suffix. Training only ever saw 12-token canvases ending in `[EOS]` and `[PAD]`s. To a position-aware model that's a different world. Fixed: the server now pads the infill canvas to the training shape.

2. **The deeper one: SFT-style prompt protection removed the capability.** The trainer never masks question positions — loss lands only on the answer region. Which means in 20,000 steps the model *never once predicted an operand digit*. Infill of the left-hand side isn't degraded; it was never trained. The bidirectional architecture supports it fine — the objective just never asked.

The fix is a `--prompt-mode mix` flag: half the batches train with prompt protection (the solve task), half unconditionally (any position maskable, BERT-style). The mix model has to match the protected model on heldout solve accuracy before it takes over as the demo checkpoint — if mixing costs solve accuracy, that trade gets documented, not hidden.

Filed under: the demo you advertise is a training objective you have to actually train.
